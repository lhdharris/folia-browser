# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

**Folia Browser** — a frameless, transparent, single-page Electron browser (`electron-app/`) that wraps a `<webview>`. Each invocation of `folia-browser <url>` opens a new window; there are no tabs by design. Every link that wants a new context (`target="_blank"`, `window.open()`, OAuth popups, middle-click) opens its own BrowserWindow. The `.desktop` entry registers it as the http/https/html MIME handler.

Distribution is via `.rpm` + `.deb` for Linux, `.exe` (NSIS installer) for Windows, and `.dmg` for macOS — all produced by `electron-builder`. macOS must be built on a Mac (electron-builder cannot cross-compile macOS targets from Linux).

## Common commands

```bash
# Run in dev (from electron-app/)
cd electron-app && npm install && npm start
cd electron-app && npm start -- https://example.com   # pass a URL

# Build Linux installers (.rpm + .deb)  →  electron-app/dist/
cd electron-app && npm run build:linux

# Build the Windows installer (.exe via NSIS); needs `wine` on Linux hosts
cd electron-app && npm run build:win

# Build the macOS .dmg — must be run on a Mac (cross-compile from Linux is unsupported)
cd electron-app && npm run build:mac
```

Build prerequisites on the host machine: `.rpm` needs `rpm` (preinstalled on openSUSE); `.deb` needs `dpkg` and `fakeroot` (`sudo zypper install dpkg fakeroot` on openSUSE); `.exe` from a Linux host needs `wine`.

There is no test suite or linter configured.

## Architecture notes that aren't obvious from a single file

- **The `electron` dependency is Castlabs ECS** (`https://github.com/castlabs/electron-releases#v42.0.0+wvcus`), not stock Electron. Vanilla Electron has no working Widevine integration; ECS adds Chromium's Component Updater Service so the CDM installs on first launch. `main.js` `await`s `components.whenReady()` before opening any BrowserWindow. On Linux, the first-time CDM install requires an app restart before EME works (sandboxing, per Castlabs docs). Full setup notes in `DRM_SETUP.md`. The Castlabs supported-versions window is ~1 year of Chromium releases — when v42 falls out of support, bump to the latest `+wvcus` release in `package.json`.

- **Single shared cookie jar.** The `<webview>` in `renderer/index.html` carries `partition="persist:folia"` as a hard-coded HTML attribute, so every window — regardless of hostname — uses the same persisted session. This is what makes one Google login carry across Gmail, YouTube, Claude OAuth, etc. (1.0 used `persist:<hostname>` set per navigation in `toolbar.js`, which broke every cross-site SSO flow.) Profile lives under `~/.config/folia-browser/Partitions/folia/` (Linux) or `~/Library/Application Support/folia-browser/Partitions/folia/` (macOS) and survives uninstall. Old `persist:<hostname>` directories from 1.0 installs are left in place — orphaned, but reachable by the Settings → "Delete cookies/cache" actions because `eachSession()` enumerates the `Partitions/` dir.

- **Frameless window, opaque, no OS chrome.** `BrowserWindow` is created with `frame: false` and a solid `backgroundColor: '#ffffff'` (no `transparent: true`); `#app` in `style.css` is `position: fixed; top/left/right/bottom: 0` so it fills the whole window. Window controls (close, maximize, sticky-note shrink) are HTML buttons that round-trip through `preload.js` → `ipcMain` handlers in `main.js`: `wm-close`, `wm-maximize`, plus the sticky-note trio `wm-sticky-shrink`/`wm-sticky-restore`/`wm-sticky-new-window` (there is **no** `wm-minimize` — the OS minimize gesture has been replaced wholesale by the sticky-note flow; see the next bullet). The preload bridge is the only API exposed to the renderer (`window.wm`). Maximize uses native `win.maximize()`/`win.unmaximize()` — no `preMaxBounds` bookkeeping. On Linux only, an `enter-full-screen` listener flips F11 fullscreen back to `win.maximize()` so the toolbar stays visible (gated behind `_htmlFullscreen` so YouTube et al. can still go true-fullscreen); macOS and Windows skip this intercept because their native fullscreen gesture is what users expect there.

- **Sticky-note minimize.** The toolbar's old minimize button has been replaced by a sticky-note shrink: clicking it animates the actual `BrowserWindow` down to a small on-desktop "post-it" carrying the action label ("Visited ctvnews.ca", "Searched for 'html colour yellow'") plus an editable italic comment. The webview is `display: none`'d but kept alive — audio/video/network keep running — so restoring is a real OS resize back to the captured bounds, not a reload. Cross-platform pieces:
  - **Per-window state on the BrowserWindow object.** `win._sticky = { originalBounds, stickyBounds }` is captured at shrink time and cleared on restore; presence of `_sticky` is the "is shrunken" flag. `stickyBounds` is the exact target rect — the `maximize` listener uses `unmaximize() + setBounds(stickyBounds)` to revert WM-initiated maximizes (drag-to-top, dblclick-on-titlebar) without the few-pixel drift that bare `unmaximize()` accumulates each cycle on Wayland. `cascadedBoundsFrom(opener)` reads `opener._sticky?.originalBounds || opener.getBounds()`, so a new window opened from the sticky's `+` button cascades off the *pre-shrink* size, not the postage-stamp.
  - **Locked colour piggybacks on the hue map.** `windowHues` entries are now `{hostname, hue, lockedColor}`. Shrinking a hueless lone window writes `lockedColor = '#FFFFE0'`; `recomputeHues` skips locked entries (so yellow stays yellow as siblings come and go), and `colorForEntry` returns `lockedColor || hsl(hue, 50%, 90%) || null` — the renderer applies whatever string main pushes via the `window-color` IPC. The "restore-to-grey if still alone" rule lives in the `wm-sticky-restore` handler: if `BrowserWindow.getAllWindows().length === 1` and the entry has a `lockedColor`, clear it and broadcast `null` (recomputeHues' null→null short-circuit means we have to send the broadcast directly).
  - **Always-on-top is hardened for Wayland.** `pinStickyOnTop(win)` calls `setAlwaysOnTop(true, 'screen-saver')` *and* `setVisibleOnAllWorkspaces(true, {visibleOnFullScreen: true})`, applied **before AND after** `animateBounds` — Mutter / KWin sometimes drop the level when bounds change, so re-applying after the resize sticks. `'floating'` is too low; only `'screen-saver'` survives. macOS/Windows honour the first call and the double-apply is harmless.
  - **`animateBounds(win, target, ms)` branches on platform.** macOS uses Cocoa's native `setBounds(target, true)` (no completion callback, so resolve via `setTimeout(ms)`). Everywhere else uses a JS-driven `setBounds` tick at `ANIM_TICK_MS = 30` (~33 fps) with easeInOutQuad — 16ms ticks queued faster than Wayland compositors can drain and looked choppy; 30ms gives breathing room. Always returns a promise that resolves at animation end so the renderer can sequence "focus the comment area after shrink" via `await window.wm.shrinkToSticky()`.
  - **Settings broadcast → `--sticky-zoom` CSS variable.** Every sticky internal dimension (padding, font sizes, action-button size) is `calc(Xpx * var(--sticky-zoom, 1))` in `style.css`, and the *window* size scales the same way (`stickyBoundsFor(cur)` multiplies `STICKY_BASE_W/H` by `settings.zoom`). `settings-save` in main re-resizes any currently-`_sticky` window and fans out a `settings-changed` IPC to every renderer; toolbar.js's `applyStickyZoom(zoom)` writes the CSS var on `:root` so live zoom changes reflow open stickies without restart.
  - **Title text comes from `composeStickyTitle()` in toolbar.js**, which joins module-level `actionVerb` (`'Visited' | 'Searched for'`) and `actionLabel` (hostname or query). Both are set when the URL bar's static label is placed; sticky button stays disabled until then (no useful title for a blank window).
  - **Action icons use a hover-revealed array, not a popover.** A Wayland popup BrowserWindow ignored `(x,y)` and opened mid-screen, and clicking the menu button broke the drag region. The current layout is three buttons (`+`, square, `×`) absolutely positioned top-right inside `#sticky-overlay`, `opacity: 0; pointer-events: none` by default, flipped to `opacity: 1; pointer-events: auto` on `#sticky-overlay:hover`. **Restore is solely via the hover-revealed maximize button** (`#sticky-restore`).
  - **Drag is `-webkit-app-region: drag` on `#sticky-overlay`.** This was deliberately *not* the case in an earlier iteration — that version used renderer JS (`mousedown` → `mousemove` → `setBounds({x,y,…})` in main) to avoid the WM's titlebar gestures (dblclick→maximize, drag-to-top→snap). That version worked on X11 and macOS but did **not** work on Wayland: Wayland's protocol forbids clients from positioning their own windows, so neither `MouseEvent.screenX/Y` in the renderer nor `BrowserWindow.setBounds({x,y,…})` in main can actually move a window — the only path to a move on Wayland is the compositor handling it via `xdg_toplevel.move()`, which is what `-webkit-app-region: drag` triggers. `#sticky-comment` and `.sticky-action-btn` opt back out with `no-drag` so the comment is typeable and the action buttons receive clicks.
  - **Fixed-size pinning + dblclick = restore.** Two mechanisms keep the sticky's size and position stable against Mutter's titlebar gestures: (1) after the shrink animation, `setMinimumSize`/`setMaximumSize` are clamped to `stickyBounds.width/height`, telling the compositor the window is fixed-size, so drag-to-top edge-snap and any actual maximize can't resize it (and `wm-sticky-restore` resets these to `(0,0)` before animating back up). (2) Mutter still fires the `maximize` state-flag change on dblclick despite min=max, and we can't make the dblclick truly inert — every post-hoc reaction is visibly broken: `unmaximize()` alone shaves a pixel each cycle (Wayland configure-event race), doing nothing strands the window in the top-left corner where Mutter moved it, and `unmaximize() + setBounds(stickyBounds)` accumulates shrink each cycle (the original "shrinks to nothing" bug). Instead we **repurpose** the gesture: the `maximize` listener fires `sticky-restore-requested` over IPC, and toolbar.js calls `restoreFromSticky()` — dblclicking a sticky restores it, same as the maximize-square action button. The upcoming `animateBounds` to `originalBounds` wipes any size drift from the unmaximize call, so the user never sees it.
  - **Audio indicator** is a speaker glyph left of the title that toggles via `audio-state-changed` on the guest webContents — main forwards the boolean over `audio-state` IPC, and toolbar.js toggles `.audible` on `#sticky-audio-icon` (CSS flips it from `display: none` to `display: inline-flex`).
  - **TDZ trap in `toolbar.js`:** `init()` is called at the **bottom** of the file, not the top. `const stickyBtn = …` (set up by `enableStickyButton()`) is hoisted as a binding but uninitialised until that line executes — calling `init()` early throws `ReferenceError`. If you reorder this file, keep the bootstrap call last.
  - **Persistence across restarts (Chrome-style tab restore).** Stickied windows persist to `userData/stickies.json` (debounced ~200ms write on shrink, restore, comment edit, sticky-window drag, and close; flushed synchronously on `before-quit`). Each entry stores `{url, verb, label, comment, originalBounds, stickyBounds, lockedColor, hostname}` — enough to rehydrate. On launch, before any other window opens, `loadStickiesFromDisk()` re-creates each as a *lazy* sticky: the BrowserWindow opens at the saved bounds with `_sticky` already populated (`deferredUrl: entry.url`, `lazy: true`), `pinStickyOnTop` applied, and `setMinimumSize`/`setMaximumSize` clamped to the sticky size — but the renderer queries `get-init-state`, paints the overlay from saved title/comment, and **never sets `src` on the webview**, so no guest process spawns until the user maximises. On restore, `wm-sticky-restore` returns `{deferredUrl}` and the renderer calls the existing `startLoad(url)` after the grow animation (the 50ms post-layout deferral guards against the "tiny initial viewport" bug documented in the next bullet). Move-tracking is gated on `show + 250ms`: on Wayland the compositor ignores the initial `x/y` hint and fires `move` events as it places the window, which without the gate would immediately overwrite the saved bounds for every restored sticky. Saved bounds are clamped to `screen.getDisplayMatching().workArea` so a monitor disconnected between sessions doesn't strand the sticky off-screen. Every launch opens a fresh browse-ready window alongside the restored stickies — `folia-browser` with stickies on disk = stickies + a new blank window. (Same rule for macOS dock-icon activation when only stickies are visible, via the `onlyStickyWindowsOpen()` check in `app.on('activate')`.) A parked sticky can't load a URL until it's restored, so surfacing only stickies on launch would leave the user with nothing to browse from. Regular non-sticky windows are not persisted; only stickies survive across launches.

- **Webview src must be set after layout.** `renderer/toolbar.js` defers `webview.setAttribute('src', url)` until `window.load + 50ms`. Setting `src` earlier locks the guest viewport to whatever tiny size the `<webview>` had during the frameless/transparent window's async layout, and the page renders permanently at that size. The `dom-ready` handler also fires a synthetic `resize` to nudge the guest if the element resized after guest attach. Don't "simplify" this — the comment in the file is the bug history.

- **URL bar → action label**, also in `renderer/toolbar.js`. The URL bar is a one-shot input on a blank window: on Enter it fades out, gets removed from the DOM, and is replaced by a static label (`#action-label`) that says either "searched for '…'" or "visited <hostname>" — set once, never updated. The classifier mirrors `main.js`'s `resolveUrl` heuristic.

- **Single-instance behavior:** `app.requestSingleInstanceLock()` plus a `second-instance` handler means subsequent `folia-browser <url>` invocations open a new window in the existing process rather than starting another Electron. URL parsing for argv ignores flags (`!a.startsWith('-')`) so Electron flags don't get confused for the URL.

- **Popup handling:** the `<webview>` tag in `renderer/index.html` carries `allowpopups` — without it, Chromium silently drops `window.open()` inside the webview's renderer and `setWindowOpenHandler` never fires. With it set, `setWindowOpenHandler` in `main.js` splits on disposition: `new-window` (OAuth popups, `window.open(url, name, "width=…,height=…")`) is allowed as a real popup so `window.opener.postMessage` and `window.close` can round-trip the auth handshake — the OS frame is the trade-off. Everything else (`target="_blank"`, plain `window.open(url)`, middle-click) is denied at the popup layer and re-opened via `createWindow(newUrl)` — the same code path the menu's "New window" uses — so it gets the full Folia shell (toolbar, frameless rounded chrome, shared `persist:folia` partition from `renderer/index.html`). `save-to-disk` is denied; downloads come through `session.on('will-download')`.

- **Auto-updater is hand-rolled, not `electron-updater`.** `electron-app/updater.js` hits `api.github.com/repos/lhdharris/folia-browser/releases/latest` on app start, compares `tag_name` (stripped of a leading `v`) to `app.getVersion()`, and on a positive diff shows a native dialog. Accepting calls `session.fromPartition('persist:folia').downloadURL(assetUrl)` so the download flows through the same `will-download` pipeline as webview downloads — the toolbar's download ring shows up exactly the same way. Because main-initiated `will-download` events arrive with `wc` set to the session's own webContents (not a guest), `findOwningWindow(wc)` returns null and the UI would never see the events; `setPendingDownloadOwner(win)` is set right before `downloadURL` and consumed (exactly once) by the handler as a fallback. Installer format selection: `darwin→dmg`, `win32→exe`, Linux reads `/etc/os-release` ID and ID_LIKE — Debian-family (debian/ubuntu/mint/pop/kali/raspbian) gets `.deb`, everything else falls through to `.rpm`. The check is gated on `app.isPackaged` and runs once per process. The user runs the downloaded installer manually; the app never auto-installs (rpm/deb need sudo, and replacing the running binary mid-launch is fragile). First-time setup: releases must exist at `github.com/lhdharris/folia-browser/releases` with `tag_name` ≥ a SemVer (`v1.1.4` or `1.1.4` both work) and assets named with the expected extensions — electron-builder's defaults already match (`folia-browser_X.Y.Z_amd64.deb`, `folia-browser-X.Y.Z.x86_64.rpm`, `Folia Browser-X.Y.Z.dmg`, `Folia Browser Setup X.Y.Z.exe`).

- **`electronDownload` mirror in `package.json`** points electron-builder at Castlabs' GitHub release assets (`v${version}` tag, `electron-v${version}-${platform}-${arch}.zip` filename). Without this, electron-builder defaults to the official Electron mirror, which doesn't have `+wvcus` releases — cross-platform builds (e.g. Mac from Linux) would fail silently with a "version not found" download error.

## Things to know before editing

- The renderer is locked down by CSP (`default-src 'self'; script-src 'self'`) — no inline scripts, no remote scripts. The `<webview>` is the escape hatch for arbitrary web content.
- Do not commit `electron-app/dist/` (build output) or `electron-app/node_modules/` — both ignored via `.gitignore`.
